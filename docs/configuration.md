# 配置模型、资源与测量协议

InferBoost 提供可复现的默认配置。使用者根据模型、设备、数据和目标负载调整参数；每次任务保存实际配置，报告中的结论仅对应这份记录。

## 模型与工作目录

| 项目 | 入口 | 配置方式 |
| --- | --- | --- |
| 主模型 | 向导 / `--model` | 填写容器内可访问的完整模型目录 |
| MTP 草稿 | 向导 / `--mtp-model` | 可选；没有草稿则留空；同目录草稿填同一路径 |
| 工作目录 | `PIPELINE_WORKSPACE` | 指向可写目录；跨实例保留需使用平台持久卷 |
| 测试数据 | 向导 / `--dataset` | JSON / JSONL；带答案才能做独立评分 |
| 量化配置 | `--quantization-config` | 复制 `configs/quantization.example.json` 后修改 |
| 推理配置 | `--inference-config` | 复制 `configs/inference.example.json` 后修改 |

源码开发在自己的运行时中填写 Python 路径；镜像已配置隔离环境。主机路径与容器路径通过挂载映射，向导填写容器看到的路径。

## 资源参数

| 参数 | 默认值 | 调整依据 |
| --- | --- | --- |
| `runtime.max_jobs` / `--max-jobs` | 2 | 编译进程并发；依据编译阶段 CPU 内存余量调整 |
| `--gpus` | `0` | 多卡分担量化；性能统一在第一张卡测量，推理 TP=1 |
| `server.max_model_len` / `--max-model-len` | 32768 | 根据模型上限和真实输入输出长度设置 |
| `server.max_num_seqs` | 4 | 同时调度的序列上限，需覆盖评测并发 |
| `server.gpu_memory_utilization` | 0.9 | 引擎显存预算比例，需为其他使用方预留空间 |
| `server.startup_timeout_seconds` | 2400 | 服务加载、编译和预热的最长等待时间 |
| `minimum_memory_gib`（量化） | 32 | 最低资源检查阈值，不是模型峰值估算 |

编译并发、量化并发和请求并发控制不同工作。进程总内存还包括模型加载、校准缓存和中间张量；显存还包括执行工作区、CUDA Graph 和 KV Cache。根据各阶段的实际峰值分配资源，不能用一个并发值代替总内存预算。

磁盘需要容纳输入权重、所有候选、校准数据、运行缓存和日志。首次使用可选择少量配方验证资源，再增加候选；仅按量化后的文件大小预留空间不足以覆盖中间产物。

## 校准、评分与性能

| 目标 | 配置 |
| --- | --- |
| 校准规模 | `--calibration-count`、`--calibration-tokens`；标准模式 512 条、每条最多 4096 token |
| 第一阶段性能轮数 | `--performance-repeats`；标准模式 3 轮，质量另测 1 轮 |
| 第一阶段推荐门槛 | `quality_gate.max_drop_pp`、`quality_gate.max_regressions` |
| 第一阶段选择偏好 | `--selection-objective size/latency/quality` |
| 加速初筛规模 | `--screening-samples`、`--search-trials` |
| 加速完整复测轮数 | `--final-repeats` |
| 加速排序缓存状态 | 推理配置 `search.objective_cache`，默认 `warm` |

默认量化门槛允许百分制下降最多 5 分且新增退化题最多 3 道。需要严格对照时，在量化配置中设置：

```json
"quality_gate": {
  "max_drop_pp": 0.0,
  "max_regressions": 0
}
```

该片段应替换配置中的同名字段，不是独立配置文件。阈值仅控制推荐；完整性、真实加载和 MTP 校验仍须通过。旧任务使用冻结配置，变更规则时新建任务。

工作流会根据模式设置校准和评测预算，CLI 显式参数用于覆盖支持项。开发自定义校准策略时使用单阶段入口，并检查保存的阶段配置。[CLI 手册](cli-reference.md) · [数据格式](data-and-evaluation.md)

## 运行方式与端口

| 运行方式 | 服务生命周期 | 端口与健康检查 |
| --- | --- | --- |
| 量化 / 加速实验 | 按候选启动并停止测试服务 | 两阶段默认内部端口分别为 18450 / 18550，可在各自 `server.port` 修改 |
| 持续推理部署 | 启动选定部署包并持续服务 | 由 `--host`、`--port` 指定，健康接口为该端口的 `/health` |
| 平台在线开发 | 使用平台开发入口 | 与推理服务分别配置，参见平台适配文档 |

实验任务使用开发实例或批处理生命周期，不依赖一个持续监听的模型服务端口。持续部署时将容器监听端口、平台端口映射和健康检查指向同一服务，并为初始化预留启动宽限时间。

示例采用 9001 作为部署端口，它不是所有平台的强制值。Docker 安装器的 `--port` 将容器 9001 映射到指定宿主端口，绑定在 `127.0.0.1`；使用安装器映射时，容器中的服务需监听 9001。外部访问、认证与 TLS 根据部署环境配置。

## 版本与任务隔离

源码提交、镜像构建和任务启动是三个独立动作。源码推送到 GitLab 后，需要重新构建并发布镜像，新的实例才会包含改动。已初始化的工作区保存应用身份，升级时使用新工作目录；旧任务继续使用原版本与原模型路径。

中断后的恢复会核对代码、模型、配置和数据；使用相同条件才可续跑。变更条件时创建新任务，已有报告和权重作为独立结果保留。[发布与同步](release-readiness.md)
