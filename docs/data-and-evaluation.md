# 数据与评测

## 三类数据，各自承担什么工作

| 数据 | 默认文件 / 来源 | 用途 |
| --- | --- | --- |
| 校准 | PerfectBlend 固定 revision 的 512 条，最多 4096 token / 条 | 让量化算法观察激活分布、估计量化误差 |
| 独立质量 | `data/quality100.json`，100 条规则题 | 原模型与量化候选对照，第二阶段另行质量复核 |
| 性能请求 | `data/public100.json`，100 条文本请求 | 第二阶段固定负载下的 TTFT / E2E / TPS |

公开分发不附带上游校准原文。首次量化由量化环境从固定 revision 读取所需条数，输出冻结 token 和来源记录；后续候选复用该任务的冻结数据。离线用法见下方说明。不同 tokenizer 会产生不同 token 数；4096 是截断上限，不会把短样本都填满。校准与评分检查完整消息和规范化用户文本交集，不声称已做全面语义去重。来源与许可见 [第三方说明](../THIRD_PARTY_NOTICES.md)。

## 自定义数据格式

JSON 文件是非空数组；JSONL 每行一个对象。每条需要唯一字符串 `uid`、非空 `group` 和文本 `messages`。不支持把图片、音频测试混入当前文本评测契约。

```json
{"uid":"custom-001","group":"arithmetic","messages":[{"role":"user","content":"7+8等于多少？只输出数字。"}],"expected":15,"scorer":"number"}
```

| scorer | 规则 |
| --- | --- |
| `exact` | 去除首尾空白后与答案文本完全相同 |
| `number` | 解析为有限数值后比较，例如 15 与 15.0 相同 |
| `json_exact` | JSON 结构和值匹配；对象键顺序不影响，数组顺序影响 |
| `json_fields` | 检查答案对象内指定字段，允许额外字段 |

JSON 默认不接受 Markdown 围栏；确需允许时在样本显式设置 `allow_code_fence: true`。`expected` 与 `scorer` 必须配套。无答案的样本可以测试性能，但不会生成准确率。程序只把 `messages` 发给模型，答案和评分器在本地评测使用。

`workflow --dataset` 会在第一阶段保留默认题并另列用户数据结果；第二阶段用用户数据做性能测试，并对其中带答案的样本复核。无答案不会被程序补出一个分数。

## 如何阅读结果

规则得分是完成评测后“匹配标准答案”的比例，不是通用智能或业务准确率。不完整的请求不产生可推荐的完整成绩。原模型与候选使用相同输入与生成参数，报告保留原对现错的退化题和原始回答。

量化默认推荐门槛：每份带答案数据相对原模型的**百分制总分下降不超过 5 分，且原模型答对、量化后答错不超过 3 道**，两项同时满足后再按权重大小等所选目标排序。配置为 `quality_gate.max_drop_pp=5.0`、`quality_gate.max_regressions=3`。例如 100 题原模型全对，量化后新增 3 道错题可通过，新增 4 道不通过；3 道是绝对数量，不是 3%。数据规模变化时，5 分条件仍同时生效。

答错题可以在上述范围内接受，但量化失败、请求报错、截断、缺失评测或未评分不能当成质量通过。这个规则只产生建议；用户可以明确选择已经完整测试但超出门槛的候选，报告仍保留退化事实。终端、Markdown、HTML 会显示任务实际门槛；显式配置的严格规则和历史任务的冻结配置保持原样，不因升级自动改变。第二阶段另对加速配置进行相对同模型基准的质量复核。

加速默认建议：当前测试下质量达标且完整的候选中，warm 平均 E2E 较低者。查看 TTFT 与显存等代价后再选择；单请求更快不代表高并发吞吐更好。

cold/warm 均在启动和预热后计时。cold 每次清除前缀缓存，warm 紧接着重复同一请求。初始化、编译与预热记录在日志，不混入请求延迟。MTP 接受率须看统计区间；旧日志的混合区间估计不当成纯性能请求实测。

默认第一阶段和第二阶段的性能输入不同，不能直接用两阶段的耗时相乘得到总加速比。要比较 BF16 原始模型、量化基础模型与最终加速方案，应另在同一数据、硬件和协议下复测。

进一步阅读：[报告与指标](reporting.md) · [量化细节](quantization-architecture.md) · [加速协议](stage2-inference.md)。


## 工作流的测量轮数

标准模式第一阶段：独立质量请求1轮，性能3轮，所有候选及原模型使用相同样本、采样参数和运行条件。每轮性能单独预热，cold/warm分别保存；默认C1 cold表报告各轮均值的平均与轮间样本标准差，不能解释为总体置信区间。完整性检查覆盖所有配置的并发和缓存条件，缺失或失败不纳入推荐。

默认100题、C1、cold/warm时，每候选100质量请求＋600性能请求，另有不计时预热。快速体验只用10题和1性能轮。质量temperature=0、seed=0；若要研究随机生成质量，应另设随机种子协议，而不是把重复同题算作更多独立题目。第二阶段仍按其自身复测与质量复核协议。

## 离线校准

在可联网且有量化运行环境的机器上，使用 `scripts/prepare_official_calibration.py` 可按指定模型的 tokenizer 预先冻结数据。完整工作流默认采用固定版本的上游数据；如已有原始 JSONL 快照，在自定义量化配置的 `calibration.raw_data` 中填写它的绝对路径，并同时提供同名 `.manifest.json` 来源清单。来源清单必须匹配固定数据集、revision、记录数量和文件 SHA256，错误时停止而不替换样本。

下载的样本、Hugging Face 缓存及任务结果写入自己的工作卷，不应提交到代码仓库。启动时确认网络能够访问 Hugging Face；下载失败时日志会保留错误，不会用评测题代替校准数据。
